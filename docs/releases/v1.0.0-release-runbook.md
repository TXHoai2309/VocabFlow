# VocabFlow v1.0.0 Production Release Runbook

**Status:** production preflight preparation; not authorization to mutate or deploy.
**Release tag:** `v1.0.0` (not created).

## Verified deployment shape and release scope

- One Cloudflare Worker named `vocabflow` serves the web SPA and `/api/*` from
  the same origin. Cloudflare's SPA fallback handles browser refreshes; API
  requests are routed to the Worker first.
- The Worker accesses Neon server-side through `DATABASE_URL`. Browser bundles
  must contain neither database credentials nor Neon provider credentials.
- Canonical production target from `config/database-targets.ts`:
  Neon project `shy-hill-72364426`, branch `br-rough-silence-b3gbqjcb`, database
  `neondb`. This is configuration evidence only; this task did not verify the
  branch by connecting to Neon or call the Neon API.
- Worker runtime context is `cloudflare-production` with production markers.
  Release CLI context is intentionally `local-development` plus both database
  markers set to `production`; every production command still requires the
  explicit production target. Shared CI and development markers cannot confirm
  production.
- Production origin and Cloudflare zone are not configured. The owner must
  choose `BETTER_AUTH_URL` (a canonical HTTPS origin) and
  `CLOUDFLARE_ZONE_NAME` before a production build can proceed. No hostname is
  guessed or embedded here.
- The owner-provided development acceptance baseline is: automated suite,
  Playwright E2E, Core CI, Trusted DB, and owner smoke pass; schema through
  migration 0012; 213 curated imported rows plus 30 starter rows (243 enabled);
  US-41 post-apply idempotency passes. This task does not re-run Trusted DB or
  independently re-attest those historical development/remote results.
- Frozen release scope: no feature work, content edits, curation manifest
  changes, learner-data changes, or release version bump. Package version stays
  `0.1.0`; `v1.0.0` is a product release tag to create only after smoke checks.

## Required order and exact commands

Run all commands from a clean checkout of the approved release SHA, with Node
`22.23.2` and pnpm `11.17.0`. The guarded build/deploy scripts refuse a dirty
tree, missing SHA, wrong toolchain, missing hostname/zone, or artifact mismatch.

1. **Verify release SHA.** Check out the intended `TXH` release commit and set
   `VOCABFLOW_RELEASE_SHA` to its full SHA. Verify `git rev-parse HEAD` matches
   and `git status --porcelain` is empty. Do not include local-only changes.
2. **Verify remote gates.** On that exact SHA require Core CI and Trusted DB
   Integration both green. Trusted DB must use only the canonical `shared-ci`
   target. A green result for an older SHA is not sufficient.
3. **Verify production config/secrets.** Resolve the owner-selected HTTPS
   origin and zone. Create/prepare the `vocabflow` Worker without a public
   route, provision the two Worker runtime secrets, and verify the separate
   operator credentials/roles. Never print or commit secret values.
4. **Production read-only DB preflight.** With operator markers/secrets loaded:

   ```powershell
   pnpm db:production-preflight -- --target production
   ```

   Require canonical protected identity, expected production branch/role,
   readable migration ledger, and `DATABASE_MUTATIONS=0`. If the branch,
   identity, or state is unexpected, stop; do not infer it should match dev.
5. **Production migration dry/safety check.** This checks provider identity,
   post-connect database identity, the ledger, pending migration hashes, and
   the production forward-only SQL guard. It is read-only:

   ```powershell
   pnpm db:migrate -- --target production
   ```

   Require the owner-reviewed pending set. Before the first production
   migration, take and verify a Neon backup/snapshot and record its recovery
   point. Stop on destructive SQL, an unexpected pending migration, or a
   non-forward-compatible release.
6. **Migrate production only after explicit owner approval.** This is the first
   database mutation in the runbook:

   ```powershell
   pnpm db:migrate -- --target production --apply `
     --confirm-target production `
     --confirm-branch br-rough-silence-b3gbqjcb
   ```

   There is no generic force/unsafe option. The migration role is required;
   reset, truncate, schema/table/type/column drops, deletes, and direct updates
   to existing rows are blocked. Do not reverse migrations to roll back.
7. **Verify ledger/schema/data after migration.** Repeat steps 4 and 5 and
   require no pending migrations, canonical protected identity, and all
   application tables present. Compare preserved business-data counts with the
   pre-migration snapshot; investigate any unexplained change before continuing.
8. **US-41 production dry run:**

   ```powershell
   pnpm vocab:curate -- --target production
   ```

   This requires `PRODUCTION_DATABASE_URL` and Neon provider proof and runs the
   curation plan in a PostgreSQL read-only transaction. Do not assume production
   equals development. The intended post-apply content is 30 starter plus 213
   curated imported rows = 243 enabled vocabulary rows; the manifest also
   contains 11 learning sets, five owner-reviewed meaning overrides, eight
   image quarantines, and three missing-image warnings.
9. **Owner reviews the exact plan.** Compare every count and row-level effect
   against the frozen US-41 manifest and production snapshot. Confirm no
   unexpected learner assignment, progress, review, XP, achievement, starter,
   disable, grade, topic, or set changes. If the observed production state
   differs from expectation, stop and obtain an explicit owner decision.
10. **Apply US-41 only after that review:**

    ```powershell
    pnpm vocab:curate -- --target production --apply `
      --confirm-target production `
      --confirm-branch br-rough-silence-b3gbqjcb
    ```

11. **Post-apply dry run/idempotency:** repeat step 8. Require zero pending
    changes and the expected 243 enabled total. Preserve the output as release
    evidence; do not rewrite the curation manifest during release.
12. **Build and deploy Worker + SPA.** Set the owner-approved
    `BETTER_AUTH_URL`, `CLOUDFLARE_ZONE_NAME`, and `VOCABFLOW_RELEASE_SHA` in
    the clean release environment. Build first, inspect successful scan output,
    then deploy the exact generated artifact:

    ```powershell
    pnpm build:production
    pnpm deploy:production
    ```

    The generated artifact pins the route to the owner-supplied zone, disables
    `workers.dev`, keeps SPA fallback and `/api/*` Worker-first routing, and
    contains no local `.dev.vars`, `.env` files, source maps, database URL, or
    provider secret. It writes a content digest bound to the release SHA; the
    deploy command rechecks the digest, route, origin, Worker name, and asset
    routing before upload. Wrangler deploy consumes the already-resolved
    production artifact; do not add `--env production` to `wrangler deploy`.
13. **Production smoke checklist:**

    - `GET /api/health` returns the expected healthy status.
    - Refresh `/`, `/login`, `/register`, `/learners`, `/progress`,
      `/learner-settings`, `/vocabulary`, `/topics`, `/learning-sets`,
      `/learning-sets/assign`, `/learning-sets/<id>`, `/study`,
      `/study/exercises`, and `/foundation`; each returns the SPA, not a 404.
    - `/api/auth/*` uses the canonical HTTPS origin, secure cookies, and
      same-origin trusted redirects; verify register/login/logout with an
      owner-controlled smoke account only after explicit release approval.
    - Authenticated API requests resolve through the Worker and Neon remains
      server-only. Verify vocabulary, learning sets, progress, and media.
    - Review Worker error logs for safe codes only; no credentials, SQL
      parameters, or full request headers/cookies.
    - Repeat the production read-only DB preflight and confirm no unexpected
      schema or curation drift.
14. **Tag only after smoke is accepted:**

    ```powershell
    git tag -a v1.0.0 <verified-release-sha> -m "VocabFlow v1.0.0"
    git push origin v1.0.0
    ```

    Confirm the annotated tag points to the exact CI-approved deployed SHA.
15. **Publish release notes** from that SHA, including CI run IDs, schema and
    curation evidence, smoke result, Worker deployment/version ID, and any
    owner-approved deviations. Never include secrets.

## Rollback and recovery

### Worker/web rollback

Cloudflare Worker versions capture code, static assets, bindings, and
compatibility settings. Record the last known-good version ID before release.
After confirming the incident and obtaining release-owner approval, list recent
deployments and roll back the `vocabflow` Worker to that exact version:

```powershell
pnpm exec wrangler deployments list --name vocabflow
pnpm exec wrangler rollback <last-known-good-version-id> `
  --name vocabflow --config dist/vocabflow/wrangler.json `
  --message "Rollback VocabFlow v1.0.0"
```

This immediately changes the active deployment across its routes; verify the
SPA and API smoke checklist again. If the older Worker cannot run against the
new schema, keep the forward schema and deploy a compatible hotfix rather than
rolling the database backward.

### Database and curation recovery

- Migrations are forward-only. Restore from the verified pre-release snapshot
  only under the database owner's incident-recovery procedure; otherwise ship a
  reviewed forward fix. Never reset production, recreate the Neon branch, or
  destructively reverse migrations.
- Do not blindly disable curated rows after learners may have progress. For a
  content/media issue, use a reviewed forward quarantine/disable action that
  preserves learner progress, review history, XP, achievements, assignments,
  and owner-review evidence.
- Re-run read-only identity, ledger, and curation checks before and after any
  recovery mutation. Record who approved it and the exact release SHA.

## Guardrails and current blockers

- `db:migrate` production dry run requires `--target production`; mutation also
  requires `--apply`, `--confirm-target production`, and exact configured
  `--confirm-branch`.
- US-41 production dry run requires `--target production`; apply requires exact
  target and branch confirmations. Both use purpose-specific production URLs.
- `db:reset` refuses production markers and all CLI override arguments.
  Reset-capable Trusted DB tooling accepts only `ci-test` + `test` markers.
- No production connection, migration, curation apply, deployment, user
  creation, or release tag was performed while preparing this runbook.
- Production hostname/zone are owner inputs. Production state and target
  existence were not independently queried; the canonical branch ID above is
  repository configuration, not provider verification.
